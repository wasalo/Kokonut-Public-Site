# The Kokonut Framework is the shared methodology behind Kokonut farms.

The Kokonut Framework gives farms a common baseline for:

- describing the farm and its context;
- planning development;
- applying regenerative principles;
- structuring value and impact questions;
- recording operational activity;
- producing reviewable evidence;
- learning across farms over time.

Its purpose is **not** to make every farm identical.

Its purpose is to make farms interoperable enough that local operators, contributors, reviewers, capital participants, researchers, and software systems can work from compatible information.

> **The goal is interoperability, not uniformity: shared structure where coordination benefits from it, local adaptation where land, people, markets, and regulation differ.**

## The Framework in one sentence

> **Describe the farm consistently → plan through shared phases → operate locally → record what happened → review the evidence → learn and improve.**

That sequence is more durable than any particular tool, chain, dashboard, or governance mechanism.

```mermaid
flowchart LR
    A["Local farm context"] --> B["Shared baseline record"]
    B --> C["Development phase + plan"]
    C --> D["Local agricultural execution"]
    D --> E["Operational records + observations"]
    E --> F["Review + publication"]
    F --> G["Interpretation + reporting"]
    G --> H["Farm / governance / partner decisions"]
    H --> I["Updated plan + shared learning"]
    I --> C
```

The Framework connects those steps.

It does not collapse them into one authority.

## What the Framework standardizes — and what it does not

| The Framework can standardize | The Framework should not automatically standardize |
| --- | --- |
| Baseline farm fields and terminology | Land ownership or legal title |
| Development phases | Crop mix across every farm |
| Regenerative principles | Daily agronomic decisions |
| Evidence and reporting expectations | Local labor arrangements |
| Value-accounting categories | One universal revenue-sharing model |
| Shared claim vocabulary | Community priorities in every location |
| Compatibility across records and tools | One governance mechanism for every farm |
| Review and learning structures | One technology stack for every operator |

This boundary is central to the Framework.

A shared schema can make records compatible.

It does not make the farm a franchise.

A shared development phase can organize work.

It does not make every landscape move at the same speed.

A shared evidence standard can make a claim easier to inspect.

It does not make the claim automatically true.

## Four development phases organize the farm lifecycle

The Framework currently uses four development phases.

| Phase | Primary purpose | Typical evidence |
| --- | --- | --- |
| **I — Planning & Preparation** | Understand the site, operators, baseline, design, infrastructure needs, risks, and funding requirements | Site records, schema, plans, budgets, baseline evidence |
| **II — Production & Regeneration** | Put the farm system into operation | Planting, infrastructure, field activity, production records, MRV |
| **III — Consolidation & Expansion** | Improve operational reliability, markets, recurring systems, and farm capacity | Multi-cycle records, financial actuals, training, quality controls, expanded evidence |
| **IV — Continuous MRV & Improvement** | Maintain longitudinal evidence, compare plans with actuals, report, adapt, and learn | Repeated measurements, reports, variance analysis, review records |

Phase IV is not a finish line after which measurement stops.

Evidence and learning should continue throughout farm operations.

## The Common Data Schema is the baseline — not the approval

The current Common Data Schema defines **13 required fields**.

Its purpose is to make a farm record structured enough for multiple actors and systems to work with it.

That can support:

- farm intake;
- proposal preparation;
- data ingestion;
- comparison;
- MRV linking;
- reporting;
- analysis;
- agent workflows.

It should not be interpreted as:

> “13 fields completed = farm approved, funded, verified, or investment-ready.”

Those are separate decisions.

A complete record can still contain:

- weak assumptions;
- unresolved legal questions;
- poor economics;
- insufficient evidence;
- operating risks;
- missing reviewer approval.

> **Structure makes a farm easier to inspect. It does not substitute for judgment.**

## Regenerative principles guide practice without becoming a recipe

The Framework documents five regenerative principles as the shared agricultural baseline.

They help organize practice around areas such as:

- soil cover and soil protection;
- biodiversity and diversity;
- perennial and multi-layer systems;
- animal integration where appropriate;
- on-site or biologically oriented inputs and nutrient cycling.

Those principles should guide design and review.

They should not be interpreted as evidence that a desired ecological outcome already occurred.

For example:

| Evidence level | Example |
| --- | --- |
| **Principle** | Maintain soil cover |
| **Implemented practice** | Mulch / living cover applied |
| **Measurement** | Repeated cover or soil observation |
| **Interpretation** | Evidence supports a claim about erosion or soil improvement |

The last step requires more than documenting the intention.

## Value frameworks help ask better questions

The Framework does not reduce farm value to revenue alone.

### Pillars of Value

The six Pillars of Value ask:

1. **WHAT** value is being created?
2. **WHO** experiences the value?
3. **HOW MUCH** changes?
4. **CONTRIBUTION** — what changed because of this intervention?
5. **RISK** — what may not happen or may not persist?
6. **PUBLIC GOODS** — what value extends beyond the immediate transaction?

These are analytical questions.

They do not automatically calculate or certify impact.

### 8 Forms of Capital

The Framework also uses eight capital categories:

- Natural;
- Financial;
- Social;
- Human;
- Material;
- Intellectual;
- Cultural;
- Health.

The purpose is to make different forms of value visible without pretending they are interchangeable.

A stronger financial result does not automatically compensate for ecological damage.

A biodiversity intervention does not automatically prove social benefit.

> **The Framework can hold multiple forms of value in the same analysis without declaring one form sovereign over all the others.**

## MRV supplies the evidence layer

The Framework and MRV are related but different.

**The Framework** defines shared structures, methods, phases, and interpretation tools.

**MRV** defines how operational observations become reviewable evidence.

The current MRV sequence is:

> **observe → structure → review → publish → attest when useful → interpret**

That means the Framework should not assume a fixed pipeline where every record must move through IPFS and EAS.

Different evidence may use different storage and publication paths.

EAS can add public provenance for significant records.

It does not turn a weak source record into scientific truth.

## Kokonut Intelligence implements data infrastructure around the Framework

[Kokonut Intelligence](/kokonut-intelligence) is not the Framework itself.

It provides infrastructure that can operationalize Framework concepts through:

- canonical farm records;
- operational events;
- review states;
- analytics;
- forecasting;
- reports;
- scoring;
- EAS integration on Celo;
- agent-access workflows.

The distinction matters.

A methodology can remain valid even if a software implementation changes.

And a software score should not become a new methodology merely because it can be calculated.

| Layer | Question |
| --- | --- |
| **Framework** | What structures and methods should farms share? |
| **MRV** | How should evidence and claims be handled? |
| **Kokonut Intelligence** | How do we store, review, analyze, publish, and automate around those records? |
| **Kokonut Hub** | What published farm/project information can people inspect? |

## Governance uses the Framework — it does not own the Framework's subject matter

The Framework can make a farm proposal easier to evaluate.

That does not mean every Framework question belongs to the Moloch DAO.

Different decisions have different authorities.

| Decision | Primary responsibility |
| --- | --- |
| Shared DAO treasury capital | Moloch DAO |
| Routine farm operations | Local farm operators |
| Contribution work / domain review | Guilds and relevant reviewers |
| Shared Framework schema / methodology | Framework stewards + affected domain reviewers |
| Scientific / ecological claim review | Qualified evidence reviewers |
| Technical implementation | Technical contributors within approved scope |

A Moloch proposal may fund a Framework improvement.

That vote does not make token holders the scientific, agronomic, or technical authority over the content of the method.

## Adelphi is the first live reference implementation

Adelphi is where the Framework has its clearest real-world reference.

It combines:

- locally operated land;
- farm-development phases;
- regenerative practice;
- crop and infrastructure systems;
- public-goods funding history;
- forecasts and actual records;
- MRV;
- Kokonut Hub publication;
- governance and contributor coordination.

That makes Adelphi useful for learning.

It does **not** make Adelphi a universal template.

<Warning>
  **Adelphi is a reference implementation, not proof of universal scalability.** Its crops, economics, community context, operators, biodiversity, infrastructure, and market conditions should not be copied blindly to another site.
</Warning>

[Explore Adelphi →](/ecosystem-wiki/kokonut-farms/adelphi/summary)

## Terra Viva is the next replication test

The current documentation identifies **Terra Viva** as the next major test of Framework portability.

Terra Viva is described as roughly **50,000 m² of adjacent land under agreement** entering:

**Phase I — Planning & Preparation**

That status matters.

Terra Viva is useful because it can help answer questions that Adelphi alone cannot:

- Which Framework fields transfer cleanly?
- Which methods need local adaptation?
- Which assumptions were specific to Adelphi?
- How should multi-farm comparison work?
- Which evidence can be normalized?
- Where does governance need to remain farm-specific?

It is **not yet evidence of successful multi-farm replication**.

## What the Framework can support — and what it cannot guarantee

| The Framework can support | It cannot guarantee |
| --- | --- |
| More comparable baseline records | Comparable farm outcomes |
| Better-structured funding requests | Funding approval |
| Clearer development milestones | Successful farm execution |
| Shared regenerative principles | Measured ecological improvement |
| More consistent evidence requirements | Scientific certification |
| Stronger forecast-vs-actual learning | Forecast accuracy |
| Reusable reporting structures | Impact |
| Cross-farm analysis | Identical local conditions |
| Better governance inputs | Good governance decisions |
| Agent-readable records | Correct autonomous decisions |

<Note>
  **The Framework reduces ambiguity. It does not remove uncertainty.**
</Note>

## Framework principles for this documentation sprint

As the Framework pages are improved, they should preserve these rules.

1. **Interoperability, not uniformity.**
2. **Local operators retain local operating authority.**
3. **Shared structure does not equal automatic approval.**
4. **Implemented practice does not equal measured outcome.**
5. **Forecast does not equal actual.**
6. **Attestation does not equal scientific certification.**
7. **Framework methodology and software implementation remain distinguishable.**
8. **Governance authority stays scoped to the decision being made.**
9. **Public-goods and economic arrangements should follow the approved farm-specific arrangement rather than an unsupported universal rule.**
10. **Replication claims should grow only as multi-farm evidence grows.**
