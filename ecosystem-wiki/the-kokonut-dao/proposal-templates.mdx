# A good proposal asks the right authority for one clear decision.

Proposal templates are useful only after the decision has been routed correctly.

Before copying a template, ask:

> **What authority am I actually requesting, and who legitimately holds it?**

Use Moloch for shared treasury capital, membership, \$vKKN, Loot, and binding DAO-rule actions.

Use Guild and domain review for contribution quality and specialized work.

Use farm operators for routine agricultural execution.

Use Framework and affected reviewers for shared methodology.

Use MRV / evidence review for claims.

A proposal can connect those scopes, but it should not collapse them into one vote.

| --- | --- | --- |

## Proposal flow at a glance

| Stage | What happens | Authority / owner |
| --- | --- | --- |
| **1. Route** | Identify the decision class and authority requested | Author + affected reviewers |
| **2. Draft** | Complete the relevant template | Author / proposal team |
| **3. Review** | Domain, financial, operational, evidence, legal, or technical review as needed | Qualified reviewers |
| **4. Revise** | Resolve material questions and narrow scope | Author / proposal team |
| **5. Activate** | An authorized actor moves a binding proposal into the live process | Current governance rules |
| **6. Vote when required** | Moloch decides Moloch-scoped actions | Eligible \$vKKN holders |
| **7. Grace / retention when applicable** | Current Moloch protections run before execution | Live DAO rules |
| **8. Execute** | Transaction and/or operational work begins | Authorized executors |
| **9. Evidence / acceptance** | Deliverables and outcomes are documented and reviewed | Named reviewers |
| **10. Closeout** | Variance, unresolved issues, and next actions are published | Proposal team / governance record |

<Note>
  Current documentation uses a **minimum 5-day draft baseline** and **5-day Moloch voting baseline** for applicable proposals. These are current governance parameters, not permanent rules. Verify live state before acting.
</Note>

## The common proposal base

The current Kokonut templates use the same ten-field base structure.

That structure improves comparability, but it should be supplemented with **authority, risk, dependencies, evidence, change-control, and closeout** where the proposal type requires them.

| Base field | What it should answer |
| --- | --- |
| **A. Proposal Name** | What decision are we discussing? |
| **B. Proposal Author(s)** | Who prepared the request and can answer questions? |
| **C. Proposal Team** | Who executes, reviews, accepts, or reports? |
| **D. Draft Start Date** | When did visible review begin? |
| **E. Proposal Description** | What exactly is being requested? |
| **F. Mission Alignment** | Why does this belong in Kokonut? |
| **G. Brand Usage** | Does the decision create public representation or brand obligations? |
| **H. Financial Implications** | What capital, cost, revenue assumption, liability, or token effect exists? |
| **I. Success Metrics** | What evidence will show delivery and, separately, any later outcomes? |
| **J. Next Steps** | Who does what after authorization? |

### Add these controls to every material proposal

| Control | Requirement |
| --- | --- |
| **Authority requested** | State exactly what the approving body is being asked to authorize |
| **Out of scope** | State what the approval does **not** authorize |
| **Dependencies** | List reviews, signatures, permits, schemas, partners, or operators needed |
| **Conflicts of interest** | Disclose authors/reviewers/payees with material financial or operational interests |
| **Evidence** | Link the records that support assumptions and later completion |
| **Material-change rule** | Define what can change operationally and what requires re-approval |
| **Closeout** | Define the acceptance record, final report, variance, and unresolved follow-up |

> **A proposal should be auditable before approval and closeable after execution.**

## Universal readiness checklist

Before moving toward binding authorization, confirm:

- [ ] The decision is routed to the correct authority.
- [ ] The requested authority is written explicitly.
- [ ] Local farm authority is preserved where relevant.
- [ ] Domain reviewers have reviewed the parts within their competence.
- [ ] Forecasts are labeled as forecasts.
- [ ] Impact claims are backed by evidence or clearly framed as intended outcomes.
- [ ] Budget assets, amounts, recipients, milestones, and evidence are specific.
- [ ] Conflicts of interest are disclosed.
- [ ] Dependencies and risks are visible.
- [ ] Acceptance criteria are testable.
- [ ] Material-change rules are defined.
- [ ] Execution owners are named.
- [ ] Closeout evidence is defined.
- [ ] Current Moloch parameters are verified if a binding DAO action is required.

<Warning>
  If reviewers cannot tell **what is being authorized, who executes it, how completion is proven, and what would require re-approval**, the proposal is not ready.
</Warning>

## Farm Funding Proposal

Use this template when Kokonut shared capital is requested for a **specific farm milestone**.

Examples:

- new farm onboarding;
- irrigation;
- land preparation;
- nursery or biofactory;
- poultry infrastructure;
- tools or equipment;
- a defined production-phase budget.

A farm-funding vote authorizes capital under stated conditions.

It does **not** transfer land title, replace local operators, prove forecast revenue, or grant token holders routine farm-management authority.

## What happens after approval

Approval is the beginning of accountable execution.

| Proposal type | Authorization | Execution | Acceptance / closeout |
| --- | --- | --- | --- |
| **Farm Funding** | Treasury budget / milestones | Payments + farm work by authorized operators/vendors | Milestone evidence, variance, farm records |
| **Guild Bounty** | Treasury budget | Contributor work + approved payments | Domain acceptance + contribution record |
| **Framework Change** | Method / schema approval and/or funding | Implementation + migration | Compatibility checks + published change record |
| **Partnership** | Defined external commitment | Signatures, payments, integrations, obligations | Delivery review + term/renewal decision |
| **Membership / Token** | Moloch token action | Contract / DAO execution | Token / treasury state verification |
| **Governance Amendment** | Binding governance change | Parameter / rule implementation | Live-state verification + docs alignment |

### Closeout record

Every material proposal should eventually answer:

- What was authorized?
- What actually executed?
- What was delivered?
- What changed from the approved plan?
- Which evidence supports completion?
- What remains unresolved?
- Did any forecast differ materially from actuals?
- Is another proposal or operational action required?

<Warning>
  **Do not mark a proposal “complete” merely because an on-chain transaction succeeded.** Transaction execution and real-world delivery are different statuses.
</Warning>

---

## Material changes after approval

Minor implementation details can remain within the approved scope.

Material changes should be disclosed and evaluated against the original authority.

Examples that may require an amendment or new proposal:

- material budget increase;
- new payment recipient;
- materially different deliverable;
- change to token amount;
- new legal obligation;
- new exclusivity;
- different farm operator / land arrangement;
- breaking schema change not reviewed originally;
- change to success / acceptance criteria that makes completion easier to claim;
- substantially different use of treasury capital.

> **An approved proposal is an authorization envelope, not a blank check.**

## Proposal status vocabulary

Use precise statuses.

| Status | Meaning |
| --- | --- |
| **Draft** | Being prepared; not authorized |
| **Reviewed** | Required reviews are substantially complete |
| **Active / Voting** | In the current binding decision process |
| **Passed / Authorized** | Approval exists, subject to applicable grace / execution conditions |
| **Executed on-chain** | Authorized transaction completed |
| **In delivery** | Operational work is still underway |
| **Accepted** | Defined deliverables passed acceptance |
| **Closed** | Evidence, variance, and follow-up are recorded |
| **Withdrawn** | Author stopped the proposal before authorization |
| **Rejected** | Required authorization was not granted |

This vocabulary makes governance records easier to compare with farm and contribution records.

## What proposal templates should never do

<CardGroup cols={2}>
  <Card title="Do not vote a fact into existence" icon="magnifying-glass-chart">
    A proposal can fund research or authorize publication, but it cannot make an unsupported ecological, financial, or scientific claim true.
  </Card>

  <Card title="Do not override local operators" icon="tractor">
    Farm funding can authorize capital and milestones without transferring routine agronomic authority to token holders.
  </Card>

  <Card title="Do not promise developing reputation" icon="users">
    Guild Points, thresholds, standing, and elections should not be promised as automatic bounty outputs.
  </Card>

  <Card title="Do not hide forecasts inside targets" icon="calculator">
    Crop revenue, impact, adoption, and partnership value assumptions should remain visibly modeled until actuals exist.
  </Card>

  <Card title="Do not skip compatibility" icon="database">
    Shared schema, MRV, API, and Framework changes should explain migration and affected systems.
  </Card>

  <Card title="Do not stop at the vote" icon="clipboard-check">
    Every material authorization needs execution ownership, evidence, acceptance, variance handling, and closeout.
  </Card>
</CardGroup>

## Before you copy a template

<Steps>
  <Step title="1. Route the decision" icon="layer-group" iconType="regular">
    Confirm whether the authority belongs to Moloch, a Guild/domain process, farm operators, Framework stewardship, evidence review, or more than one scope.
  </Step>

  <Step title="2. Choose the narrowest template" icon="file-signature" iconType="regular">
    Ask for only the authority required for this decision.
  </Step>

  <Step title="3. Gather evidence first" icon="magnifying-glass-chart" iconType="regular">
    Link budgets, contribution records, farm data, specifications, agreements, live DAO state, and assumptions before asking reviewers to infer them.
  </Step>

  <Step title="4. Name reviewers and executors" icon="users" iconType="regular">
    Make expertise, acceptance, transaction execution, and operational delivery distinguishable.
  </Step>

  <Step title="5. Define change-control" icon="arrows-rotate" iconType="regular">
    Decide what can change inside the approved scope and what requires renewed authorization.
  </Step>

  <Step title="6. Define closeout" icon="clipboard-check" iconType="regular">
    State what evidence will allow the proposal to move from authorized to accepted and closed.
  </Step>
</Steps>
